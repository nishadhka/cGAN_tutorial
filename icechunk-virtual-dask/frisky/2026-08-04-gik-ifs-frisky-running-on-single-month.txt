  Can Frisky calculate the DAG size?

  Not for a dask graph, no. hijack() and client.compute() both receive the graph
  after the client has built it, so the 9M-task construction — or the hang —
  happens before Frisky is involved. graph_size.py stays the right tool for 
  that.

  Frisky's submit_expression is the one path that would help: it ships the
  expression and expands it scheduler-side in Rust, off the client's GIL. But it
  needs dask@main + the dask-array Rust backend, which is exactly the git-main
  pinning that breaks the client/worker parity README.md §1 depends on — and it
  still expands to 3.76M tasks, just elsewhere.

  measure, so the size is arithmetic and known before you open anything. That's

● Checked against the installed 2.1.1 — the API is there and it maps onto our
  problem almost exactly:

  Session.fork()          -> ForkSession        (picklable, one per worker job)
  ForkSession.store       -> writable, worker writes its own region
  Session.merge(*forks)   -> None               (coordinator collects
  changesets)

  This removes the thing that just killed the run. Right now every byte flows
  worker → client → Ceph, so the client gathers 259 MB per channel inside an 8

  number, lat, lon), so one (channel, step) block is exactly one chunk: aligned,
