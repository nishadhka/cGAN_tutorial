| **Wind level mismatch** (10 m vs 700 hPa) | Wind signal ~55% of expected magnitude | Identified, fix pending |

Three additional bugs were fixed in earlier sessions (latitude flip, step index
calculation, nonnegative field list) — these are documented for completeness.

|--------|--------|---------------|-------------|
| 1 | `apcp` | `log10(1 + x)` | `data_gefs.py:274` |

**Important:** The `if/elif` structure in `data_gefs.py` has a subtle behavior:
- Line 274: `if field in ["apcp"]` — standalone `if`, NOT `elif`
- Line 280: `if field in ["msl", "pres", "tmp"]` — another standalone `if`
- Line 288: `elif field in nonnegative_fields` — this catches `cape`, `pwat`

The inference script uses `if/elif/elif/elif` which is equivalent in practice,
since the field sets are mutually exclusive.

## 5. Test 2: Precipitation Accumulation Type Analysis

### 5.1 Background

The critical question: does the training data use **total accumulated**
precipitation from hour 0, or **bucket-incremental** precipitation
(accumulated since last bucket reset)?

### 5.2 GEFS Bucket Structure

GEFS uses 6-hour accumulation buckets for APCP:

```
Bucket 1: hours  0– 6   (apcp at hour 6 = total precip in 0-6h)
Bucket 2: hours  6–12   (apcp at hour 9 = precip accumulated since hour 6)
Bucket 3: hours 12–18
...
Bucket 5: hours 24–30   (apcp at hour 30 = total precip in 24-30h)
Bucket 6: hours 30–36   (apcp at hour 33 = precip since hour 30)
```

### 5.3 Raw Data Inspection

Examined the streamed GEFS apcp data for 20240520 at steps 30 and 36:

```python
# apcp_20240520_00z.nc, member dimension
# step=30 vs step=36 comparison:
# 19 of 30 members show step36 < step30
# This CONFIRMS bucket-incremental storage (reset between steps)
```

Typical values across the ICPAC region:
- **Step 30:** ~5–10 mm (accumulated within bucket 24-30h)
- **Step 36:** ~3–8 mm (accumulated within bucket 30-36h)

### 5.4 Training Code Analysis

`data/data_gefs.py:256-266` (load_fcst):
```python
ds_path = os.path.join(FCST_PATH, yearstr, f"{field}_{yearstr}.zarr")
nc_file = xr.open_dataset(ds_path, engine="zarr", consolidated=False)
nc_file = nc_file.sel({"time": date,
                        "step": [np.timedelta64(time_idx,'h'),
                                 np.timedelta64(time_idx+HOURS,'h')]})
short_name = [var for var in nc_file.data_vars][0]
data = np.moveaxis(np.squeeze(nc_file[short_name].values), 0, -1)
```

The training code reads **raw zarr values** without any accumulation processing.
No differencing, no cumulative sum. Whatever is in the zarr IS what the model sees.

**Contrast with IFS code** (`scripts/ensemble-forecast.py:183-192`):
```python
# For accumulated fields: takes difference between consecutive steps
temp_data = nc_in[f"{field}_ensemble_mean"][0, :, in_time_idx:in_time_idx+2, :, :]
temp_start = temp_data[:, 0, :, :]
temp_end = temp_data[:, 1, :, :]
temp_diff = temp_end - temp_start  # ← differencing!
```

The IFS code explicitly differences accumulated fields. The GEFS training code
does NOT.

### 5.5 Normalization Stats Generation

`data/data_gefs.py:348-416` (get_fcst_stats_fast):
```python
# For apcp, falls through to else branch:
else:
    data = nc_file[short_name].values  # raw zarr values, no processing
```

The normalization stats reflect whatever was in the training zarr. If the zarr
stored total accumulated values (accumulated from hour 0), then at hour 30 we'd
expect values of ~100+ mm. If bucket-incremental, ~5-10 mm.

### 5.6 Hypothesis

The training zarr at ICPAC likely stores **total accumulated** precipitation
(from hour 0 to the valid time), NOT bucket-incremental values. Evidence:

1. The IFS→GEFS field mapping calls the field "Total precipitation" → apcp
2. The `apcp` zarr name suggests cumulative/total values
3. If training data used bucket values (~5-10 mm), the model should produce
   similar-scale outputs for bucket input. But the reference shows ~60 mm,
   suggesting the model was trained on much larger input values.
4. In log-space: `log10(1 + 100)` ≈ 2.0 (cumulative at hour 30) vs
   `log10(1 + 8)` ≈ 0.95 (bucket-incremental). The gap of ~1.0 in log-space
   directly explains why output magnitudes are 10× too low.

### 5.7 Impact Quantification

```
                    Bucket-incremental    Total-accumulated
                    (our current data)    (hypothesized training)
                    ------------------    ----------------------
Typical value       5–10 mm               80–120 mm
log10(1 + x)        0.78–1.04             1.91–2.08
Model sees          ~0.9                  ~2.0
Gap in log-space    ~1.1 units
Linear impact       10^1.1 ≈ 12.6×
```

This is the **primary root cause** of the magnitude discrepancy.

## 6. Test 3: Wind Level Mismatch

### 6.1 Observation

FCSTNorm_GEFS_2018.pkl normalization stats for wind:
```
ugrd: min=-43.09, max=43.72
vgrd: min=-41.20, max=43.77
```

Our 10-meter wind data from GEFS streaming:
```
u10: typical range -15 to +24 m/s (max ~24)
v10: typical range -15 to +24 m/s (max ~24)
```

After normalization: `data / max(abs(min), max)`
```
Our data:     24 / 43.72 ≈ 0.55 (underutilized range)
Training:     44 / 43.72 ≈ 1.00 (full range)
```

### 6.2 Evidence

The IFS→GEFS field mapping confirms:
```
u700 → ugrd   (700 hPa u-component wind)
v700 → vgrd   (700 hPa v-component wind)
```

The training GEFS data used **700 hPa wind** (pressure level), not 10-meter wind.
Our streaming code (`stream_gefs_for_cgan.py:79-80`) fetches:
```python
'ugrd': {'gefs_prefix': 'u10/instant/heightAboveGround/u10', ...},  # 10m!
'vgrd': {'gefs_prefix': 'v10/instant/heightAboveGround/v10', ...},  # 10m!
```

### 6.3 Impact

Wind is used as context for precipitation patterns. With only ~55% of the
expected signal range, the model receives weaker meteorological forcing.
This is a secondary contributor to the low precipitation output.

### 6.4 Fix

Update `stream_gefs_for_cgan.py` CGAN_VARIABLES to use 700 hPa wind:
```python
'ugrd': {'gefs_prefix': 'u/instant/isobaricInhPa/u', 'level': 70000, ...},
'vgrd': {'gefs_prefix': 'v/instant/isobaricInhPa/v', 'level': 70000, ...},
```
(Exact GEFS zarr path for 700 hPa wind needs verification against GIK templates.)

## 7. Previously Fixed Bugs (Sessions 2026-02-26 to 2026-02-28)

### 7.1 Bug: Latitude Flip (Fixed 2026-02-28)

**Problem:** GEFS data was fed to the model in descending (N→S) latitude order,
while the model was trained on ascending (S→N) data aligned with constants.

**Fix:** `run_gefs_inference_raw.py:600-602`
```python
lat_vals = nc_file.latitude.values
if lat_vals[0] > lat_vals[-1]:
    data = data[:, :, ::-1, :]
```

### 7.2 Bug: Wrong Step Index Calculation (Fixed 2026-02-28)

**Problem:** `compute_cgan_step_indices` treated forecast hours as positional
indices. This caused the pipeline to stream hours 87, 105, 123, 141, 159
instead of the correct hours 30, 36, 42, 48, 54.

**Fix:** Use `position = hour // 3` to convert forecast hours to GEFS step
positions:
```python
step_positions = [h // step_interval for h in step_hours]
```

### 7.3 Bug: Wrong nonnegative_fields (Fixed 2026-02-26)

**Problem:** `nonnegative_fields` was `['cape', 'pwat', 'apcp']` instead of
`['cape', 'msl', 'pres', 'pwat', 'tmp']`.

**Fix:** Matched training code definition exactly.

### 7.4 Bug: Missing Elevation Normalization (Fixed 2026-02-26)

**Problem:** Elevation constants were not divided by 10000.

**Fix:** `z = elev_data / 10000.0`

### 7.5 Bug: Wrong denormalise Function (Fixed 2026-02-26)

**Problem:** `denormalise` was returning raw power values without the -1 offset
and 100 cap.

**Fix:** `return np.minimum(10**x - 1.0, 100.0)`

## Appendix A: Normalization Code Comparison

### Training Code (`data/data_gefs.py:256-299`)

```python
def load_fcst(field, date, time_idx, log_precip=False, norm=False):
    ds_path = os.path.join(FCST_PATH, yearstr, f"{field}_{yearstr}.zarr")
    nc_file = xr.open_dataset(ds_path, engine="zarr", consolidated=False)
    nc_file = nc_file.sel(
        {"time": date,
         "step": [np.timedelta64(time_idx, 'h'),
                  np.timedelta64(time_idx + HOURS, 'h')]}
    )
    short_name = [var for var in nc_file.data_vars][0]
    data = np.moveaxis(np.squeeze(nc_file[short_name].values), 0, -1)
    data = tf.image.resize(data, [384, 352]).numpy()

    if field in nonnegative_fields:
        data = np.maximum(data, 0.0)

    if norm:
        if field in ["apcp"]:
            data = np.log10(1 + data)
            # ... ensemble mean/std ...
        if field in ["msl", "pres", "tmp"]:         # NOTE: standalone if, not elif
            data -= fcst_norm[field]["mean"]
            data /= fcst_norm[field]["std"]
            # ... ensemble mean/std ...
        elif field in nonnegative_fields:            # catches cape, pwat
            data /= fcst_norm[field]["max"]
            # ... ensemble mean/std ...
        elif field in ["ugrd", "vgrd"]:
            data /= max(-fcst_norm[field]["min"], fcst_norm[field]["max"])
            # ... ensemble mean/std ...
    return data
```

## Appendix B: GEFS Bucket Accumulation

GEFS APCP uses 6-hour accumulation buckets:

```
Hour:    0   3   6   9  12  15  18  21  24  27  30  33  36  ...
Bucket:  |---1---|  |---2---|  |---3---|  |---4---|  |---5---|  |---6---|
Reset:           ↑           ↑           ↑           ↑           ↑

At hour 30: accumulated since hour 24 (within bucket 5)
At hour 33: accumulated since hour 30 (within bucket 6)
At hour 36: accumulated since hour 30 (end of bucket 6)

Total accumulated (hour 0→30):
  = apcp(6) + apcp(12) + apcp(18) + apcp(24) + apcp(30)
  = sum of all bucket-end values through hour 30
```

To convert from bucket-incremental to total accumulated, sum all bucket-boundary
values from hour 6 through the target hour, plus any partial bucket contribution
if the target is not on a boundary.
